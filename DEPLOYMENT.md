# Azure deployment

See the [README](README.md) for local setup, the [architecture guide](docs/architecture.md) for data flows, the [function reference](docs/functions.md) for implementation details, and the [user guide](docs/user-guide.md) for operating the gallery. This document describes the current deployment; proposed improvements remain in [TODO.md](TODO.md).

## Resources

- Subscription: Visual Studio B Dev Essentials.
- Resource group: `webapps`, West Europe.
- Azure Static Web Apps: Free plan, West Europe managed API, source `main` from this repository.
- Storage: StorageV2, Standard LRS, Hot tier, HTTPS only, TLS 1.2; `gallery` Blob container exposes anonymous blob reads but not container listing. Its default Blob REST version is pinned to `2023-11-03`, so anonymous downloads return each original's `Content-Disposition` header. The `TagOverrides` Table is private.
- The photos and the catalog/research text are public. Do not store credentials or private notes in `catalog-data.js`.

## Custom domain

The public gallery is also available at `https://mimishop.michaelwhitehouse.net`. The Static Web App custom-domain binding is represented by `siteCustomDomain` in `infra/main.bicep`; set `customDomainName` when deploying a different hostname. The `michaelwhitehouse.net` Azure DNS zone is in the Visual Studio A subscription, resource group `mikenet`, while the Static Web App is in the Visual Studio B subscription, resource group `webapps`. Its `mimishop` CNAME points to the Static Web App's `defaultHostname` output. Keep the DNS record and custom-domain binding when redeploying; Azure provisions the HTTPS certificate after validation.

For a fresh environment, provision the resource group and Static Web App first: `infra/main.bicep` treats the site as an existing resource. The template also does not create the original `gallery` container, upload catalog assets, create DNS records, configure the Foundry agent, or populate the managed API SAS settings. Establish those dependencies separately. Required template parameters are `storageAccountName`, `staticWebAppName`, `catalogFunctionAppName`, `functionHostStorageAccountName`, and `foundryProjectEndpoint`; check the template for optional parameters and defaults. Review a what-if before applying infrastructure changes. The template can create a monthly resource-group budget of 5 billing-currency units with 80% and 100% notifications by setting `enableCostBudget=true` and supplying `budgetContactEmail`. Azure rejected budgets for this Visual Studio subscription's offer type, so the feature defaults off here. Grant the deploying user `Storage Blob Data Contributor` on the storage account. Set `TABLE_ENDPOINT` and `TABLE_SAS_TOKEN` in the Static Web App's API application settings; neither belongs in this repository. The Function SAS must be scoped to `TagOverrides`, HTTPS-only, and limited to read/query, add, update, and delete.

## GitHub deployment

Add the Static Web Apps deployment token as the Actions secret `AZURE_STATIC_WEB_APPS_API_TOKEN`. The workflow deploys the repository root and `api/` on pushes to `main` or when manually started from Actions. Pull requests do not deploy. This workflow currently does not run the API/worker tests or deploy `worker/`. Run both test suites under Node 22 before releasing, and deploy worker changes separately using the procedure below. The root-directory publication currently includes operational files; an allowlisted public artifact is planned in `TODO.md`. Do not place secrets in any repository file.

## Editor

Invite Mimi's Microsoft Entra account to the `catalog_editor` role in Static Web Apps Role Management. Static Web Apps role names allow letters, digits, and underscores, so this uses an underscore. The app's edit API also checks the role from the Static Web Apps principal header. Anonymous visitors can browse the catalog and read tag overrides but cannot write them.

The `/.auth/login/aad` route signs an editor in; `/.auth/logout` signs out. Import an existing local edit backup after signing in. The original photo catalog and research remain in `catalog-data.js`. New community contributions and their research are stored in `CatalogItems` and loaded through the API. Editors can also change contributor attribution and hide published contributions. Shared tag overrides sync through `TagOverrides`; photo review checks remain browser-local.

## Resumable asset upload

Generate optimized display images from the unchanged originals with `node scripts/generate_gallery_renditions.cjs --shopping-root "<Japan shopping folder>"`. It checks every original against `Catalog/move-manifest.csv`, writes immutable `Catalog/optimized-v1/` WebP and JPEG files (480 px thumbnails and 1600 px detail renditions), and checkpoints each image in `Catalog/optimized-v1-manifest.jsonl`. The generator requires `sharp` from `worker/` dependencies and checks that aggregate WebP thumbnail bytes are at least 30% below the existing JPEG thumbnail set. Inspect packaging text at full resolution before switching the catalog.

Run `scripts/upload_assets.py` from a Python environment with `requirements-assets.txt` installed and an Azure CLI login. It checks all original photo SHA-256 values against the catalog move manifest, uploads originals, old rollback assets, HEIC JPEG previews, and the new 2,964 versioned renditions, then records a private JSONL checkpoint outside this repository. It safely merges newly added rendition paths into the existing verified transfer manifest. Blob SHA-256 metadata and stored MD5 are checked remotely. Upload display assets before deploying the catalog so every new image URL exists when the site switches. Use `--skip-download-headers` during that upload so the still-live old gallery keeps its current inline behavior; after the optimized site is live, run the same command with `--headers-only` to set and verify `Content-Disposition: attachment` on original photos while preserving their bytes and other HTTP headers. The transfer manifest is private operational data and must not be committed.

The static catalog maps each image to JPEG fallback and WebP display paths and separately retains its exact source path for **Save Image**. HEIC sources display from JPEG renditions but download as HEIC. Old `photos/`, `thumbnails/`, and `previews/` paths remain available for rollback; `optimized-v1/` is immutable and versioned for cache safety. Community contributions publish their sanitized JPEG plus the same four renditions under the `contributions` container. Their full sanitized JPEG uses attachment headers. Older contribution records without rendition paths continue to use their existing photo and thumbnail fields.

## Rotate the Table SAS

The Static Web Apps managed Functions API has no managed identity. Generate a replacement service SAS for the `TagOverrides` Table with permissions `raud`, HTTPS-only, and a new expiry; update `TABLE_SAS_TOKEN` in Static Web Apps API application settings and confirm `GET /api/tag-overrides` works. Do not print, commit, or add the token to GitHub Actions. Rotate before expiry. A move to a linked Function backend with managed identity would require a separate architecture and hosting-plan decision; it is not implemented by this repository.

## Cost controls

Static Web Apps Free includes a 100 GB monthly bandwidth allowance per subscription; consult the current [quotas](https://learn.microsoft.com/en-us/azure/static-web-apps/quotas) and [pricing](https://azure.microsoft.com/en-us/pricing/details/app-service/static/) before capacity planning. Blob internet egress, storage transactions, worker execution and Foundry usage are separate cost sources. The Bicep budget defaults off because the subscription offer previously rejected budgets; it is not an active spending control. The optional budget amount is 5 billing-currency units, not necessarily GBP. A budget is an alert, not a spending cap. The worker configuration permits up to four 2 GB instances and does not configure always-ready instances; this limits scale, not total monthly cost.

## Public photo contributions

The upload form is public and does not require sign-in. It accepts JPEG, PNG, WebP, HEIC, or AVIF images up to 24 MiB each. Camera-roll selection can include multiple files; the browser uploads up to two concurrently, with one image per API request. The browser sends the original bytes directly to the Static Web Apps managed API. The API keeps the original in the private `contribution-inbox` container, stores a SHA-256 keyed draft row in `CatalogItems`, and enqueues analysis. The browser generates an unguessable 256-bit draft token, persists it with draft metadata in this origin's `localStorage` under `mimi-japan-contribution-drafts-v2`, and sends it in the `x-catalog-draft-token` request header; Table Storage stores only its SHA-256 hash. Do not log or share a draft token. Draft records receive an `expiresAt` value 30 days after creation or restart. A daily worker timer (`0 15 3 * * *`, 03:15 UTC) removes eligible expired records and files; deletion is asynchronous and depends on successful worker execution. Closing a tab does not clear persisted draft credentials. Clearing site data, changing browser/profile, or moving between the custom and default hostnames can make a private draft inaccessible. The legacy session-storage draft is migrated on startup. Tag-edit exports do not back up draft credentials.

The queue-triggered Node 22 Function App uses its managed identity for the private inbox, queue, catalog Table, public contribution container, and Foundry agent. The worker resizes and re-encodes images before calling Foundry, which removes EXIF/location metadata from generated images. Foundry returns the structured identification, Japanese-to-English translations, and web research. The complete result remains private until the visitor supplies a public contributor name and selects **Add to catalog**. Publishing copies the sanitized JPEG and four display renditions into `contributions`, verifies their SHA-256 hashes, and makes the matching Table row available to the public gallery. A duplicate upload cannot take over another visitor's private draft. Editors can hide a contribution; the API queues removal of its public images and marks its catalog row hidden. File removal is asynchronous, and previously downloaded or cached public copies cannot be recalled. A contributor can discard a private draft before publication starts; discard marks it unavailable and queues private-file cleanup. If cleanup cannot be queued, the expiry timer is the fallback.

The public app uses the following Static Web Apps API settings for intake: `CATALOG_TABLE_ENDPOINT`, `CATALOG_TABLE_NAME`, `CATALOG_TABLE_SAS`, `CATALOG_BLOB_ENDPOINT`, `CATALOG_INTAKE_CONTAINER`, `CATALOG_INTAKE_BLOB_SAS`, `CATALOG_QUEUE_ENDPOINT`, `CATALOG_QUEUE_NAME`, and `CATALOG_QUEUE_SAS`. Set the Table SAS to `rau` on only `CatalogItems`, the Blob container SAS to `rcw` on only `contribution-inbox` (read for token-gated previews; create/write for uploads), and the Queue SAS to `a` on only `catalog-intake`; all should require HTTPS and have an expiry. The API does not need permission to process queue messages or delete Table entities. Keep every SAS in server-side Static Web Apps API settings. Never put one in the app bundle, GitHub, or deployment logs. Keep the existing `TABLE_ENDPOINT` and `TABLE_SAS_TOKEN` settings for tag overrides.

The worker app settings are managed by Bicep: `CATALOG_TABLE_ENDPOINT`, `CATALOG_TABLE_NAME`, `CATALOG_BLOB_ENDPOINT`, `CATALOG_INTAKE_CONTAINER`, `CATALOG_PUBLIC_CONTAINER`, `CATALOG_QUEUE_NAME`, `CatalogQueue__queueServiceUri`, `CatalogQueue__credential`, `FOUNDRY_PROJECT_ENDPOINT`, and `FOUNDRY_AGENT_NAME`. The worker uses managed identity for these services, not SAS keys. Assign **Foundry Agent Consumer** to the Function App identity at the individual `mimishopping` agent scope. The worker calls the named agent endpoint; the deployed agent and endpoint version configuration are external to this template. Operators should pin its endpoint to a tested agent version and record that version with each release. The presence of `worker/src/catalog-schema.js` does not itself configure the remote agent.

The API writes plain JSON through the Azure Storage Queues JavaScript SDK. `worker/host.json` sets `extensions.queues.messageEncoding` to `none` to match those messages; the Queue extension defaults to `base64` and rejects raw messages before the function handler runs. Keep the producer and host setting aligned. Each processing or publication attempt also has a random ID stored on the draft; the worker checks it so a stale poison message cannot mark a newer retry as failed or overwrite a ready result.

### First deployment and verification

1. Establish the bootstrap dependencies listed above. Build and inspect the Bicep change, then deploy the infrastructure in `webapps` with the existing gallery Storage and Static Web App names and a dedicated Flex Consumption Function App plus host-storage account. The template creates the inbox, public contributions container, Table, queues, Function App, and scoped storage role assignments. Confirm the what-if does not delete or replace the existing gallery assets.
2. Assign **Foundry Agent Consumer** to the Function App managed identity at the `mimishopping` agent scope. Deploy `worker/` to the Flex Consumption app with Azure Functions Core Tools (`func azure functionapp publish <function-app-name>`) or zip `host.json`, `package.json`, `package-lock.json`, and `src/` from `worker/`, then run `az functionapp deployment source config-zip -g webapps -n <function-app-name> --src <package.zip> --build-remote true`. Check that the registered functions include the queue processor, poison-queue handler, and daily draft cleanup timer.
3. Generate the three short-scope, HTTPS-only SAS tokens described above, then set them only as Static Web Apps API app settings. Do not print tokens in the terminal or save them in the repository. Verify the settings by testing anonymous API requests rather than reading secret values back.
4. Deploy the root site and `api/` through the existing GitHub Actions workflow. Confirm the API is available before making the upload link public, then pin the production Foundry endpoint to the tested structured-output version.
5. In a separately authorized test environment, test without sign-in: upload an in-person Japanese store photo, verify the private status and token-gated preview, check the translated result and research sources, and confirm a blank contributor name cannot publish. Submit with a name, then verify the sanitized photo and catalog row become public. Also test token denial, duplicate-draft denial, editor-only hide, expiry cleanup, and a phone-sized viewport. Use a separate unpublished draft to test discard and expiry. Remove the deliberately published test contribution through the editor hide flow and verify worker cleanup; do not publish test material into production without authorization.

Static Web Apps managed API requests have a [45-second duration limit](https://learn.microsoft.com/en-us/azure/static-web-apps/apis-overview); image analysis therefore runs in the queue worker. The app enforces a 24 MiB upload cap to leave room below the platform request limit. Public upload has no CAPTCHA, per-IP limit, or daily quota, so anonymous AI use and Blob traffic can vary. The expiry timer skips published contributions; published contributions remain until an editor hides them. Private draft expiry and discard cleanup follow the asynchronous rules described above.


On 24 September 2026, read-only checks confirmed Static Web Apps Free on `main`, the custom domain binding, a running Node 22 worker with 2 GB memory and a maximum of four instances, and registration of `processCatalogContribution`, `markPoisonCatalogContribution`, and `expireCatalogDrafts`. Worker application setting names contained no Application Insights connection setting. These observations establish configuration and registration, not successful end-to-end processing or alert delivery.
